# Step 16：计算字节熵值,标记疑似加壳区段

> 模块：D 分析工具(收官) ｜ 对应提交：`<待回填>` ｜ 测试：✅ 通过 ｜ 上一步：[Step 15](step-15-strings.md)

## 0. 一句话目标
实现香农熵 `shannon_entropy`(衡量字节分布有多随机,0~8 bits/byte)和分块版 `entropy_blocks`,用"高熵"标记疑似加壳 / 加密 / 压缩的区段。

## 1. 前置回顾
Step 15 我们发现"明文字符串异常少"可能意味着加壳,但那只是间接信号。本步给出**定量**判据:**熵**。压缩 / 加密后的数据看起来像随机噪声,熵接近最大值 8;正常代码 / 文本有结构、有重复,熵明显更低。按块算熵,高熵块就是"这里可能藏着加密 / 压缩内容"的红旗。这是模块 D 收官步。

## 2. 先写测试(TDD·红)
熵有几个漂亮的边界值,正好拿来当测试:
```rust
#[test] fn entropy_of_empty_is_zero()    { assert_eq!(shannon_entropy(&[]), 0.0); }
#[test] fn entropy_of_uniform_bytes_is_zero() {
    assert_eq!(shannon_entropy(&[0x41; 100]), 0.0);   // 全同一字节 → 0
}
#[test] fn entropy_of_all_256_values_is_eight() {
    let data: Vec<u8> = (0..=255).collect();          // 256 种值各一次 → 完全均匀
    assert!((shannon_entropy(&data) - 8.0).abs() < 1e-9);  // 正好 8
}
```
注意第三个测试用 **`(h - 8.0).abs() < 1e-9`** 而非 `== 8.0`:浮点运算有微小误差,**永远不要用 `==` 比较浮点**,要比"足够接近"。`shannon_entropy` 不存在 → **红**。

## 3. 实现到通过(TDD·绿)
香农熵公式:H = −Σ pᵢ·log₂(pᵢ),其中 pᵢ 是第 i 种字节出现的概率。
```rust
pub fn shannon_entropy(bytes: &[u8]) -> f64 {
    if bytes.is_empty() { return 0.0; }
    let mut counts = [0usize; 256];          // 256 种字节各自的计数
    for &b in bytes { counts[b as usize] += 1; }
    let len = bytes.len() as f64;
    let mut h = 0.0;
    for &c in counts.iter() {
        if c > 0 {
            let p = c as f64 / len;          // 这种字节的概率
            h -= p * p.log2();               // 累加 -p·log2(p)
        }
    }
    h
}
```
- **`[0usize; 256]`**:一个长度 256 的计数数组,下标 = 字节值(0~255)。
- **`p.log2()`**:以 2 为底的对数(熵的单位是 bit,所以底为 2)。`p` 是 `f64`(64 位浮点),`log2` 是它的方法。
- **只对 `c > 0` 累加**:概率为 0 的字节不贡献(且 `log2(0)` 是负无穷,必须跳过)。

分块版,复用 Step 14 学的 `chunks` + `map`:
```rust
pub fn entropy_blocks(bytes: &[u8], block_size: usize) -> Vec<(usize, f64)> {
    bytes.chunks(block_size).enumerate()
        .map(|(i, chunk)| (i * block_size, shannon_entropy(chunk)))
        .collect()
}
```

`cargo test` → **✅ 绿(38 passed)**。真实文件:
```
熵: 整体 6.327 bits/byte
  高熵块(>7.2,4KB/块): 0 个
```
6.327 是普通(未加壳)程序的典型值;高熵块 0 个 → **判定:未加壳**。若拿一个 UPX 加壳的程序来跑,整体熵会飙到 7.5+、出现大量高熵块。

## 5. 学到的语法 / 技巧
- **`f64` 浮点与 `.log2()`**:浮点数学;对数运算。
- **浮点比较用容差**:`(a - b).abs() < 1e-9`,绝不用 `==`。
- **计数数组 `[0usize; 256]`**:用定长数组按下标统计。
- **`{:.3}` 格式**:浮点保留 3 位小数。
- **迭代器链 `chunks().enumerate().map().collect()`**:声明式地把"分块→算熵→收集"串起来。
- **`.filter(|&(_, h)| h > 7.2)`**(main 里):按条件筛选元组。

## 6. 语言设计巧思
**浮点的"近似"本质,与 Rust 不让你装作精确**。`f64` 是二进制浮点,很多十进制小数无法精确表示,运算会累积微小误差。Rust 在这点上没有特殊魔法——和所有语言一样,你必须用容差比较。但 Rust 的类型系统**逼你正视**:`f64` 不实现 `Eq`(只实现 `PartialEq`),正是因为浮点有 `NaN`(`NaN != NaN`)、相等语义不完整。这也是为什么含 `f64` 的结构体不能简单 `#[derive(Eq)]`。语言用类型把"浮点不是精确可比的"这一事实摆在你面前,而不是让你踩坑。我们的 `Symbol`/`Segment` 用整数字段所以能 `Eq`,而熵函数返回 `f64`、测试就老老实实用容差——类型在提醒你该怎么对待它。

**为什么用计数数组而非 `HashMap`**:字节只有 256 种可能,用一个定长 `[usize; 256]` 数组按下标计数,比 `HashMap<u8, usize>` 更快(无哈希、无堆分配)、更简单。"值域很小且固定时,数组索引胜过哈希表"是常见的性能直觉。

## 7. 领域知识:熵与加壳检测
- **香农熵**:信息论里衡量"不确定性 / 信息量"的指标。对字节流,它量化"下一个字节有多难猜"。全同一个字节(完全可预测)熵 0;256 种字节均匀出现(完全不可预测)熵 8。
- **典型值**:英文文本 ~4.5;普通机器码 ~6;**压缩 / 加密数据 ~7.9+**(接近随机)。
- **加壳检测**:加壳器(UPX、Themida 等)把原程序压缩 / 加密后塞进一个小的解压存根。结果是文件大部分变成高熵数据。**"整体高熵 + 大段连续高熵块"是加壳的经典指纹**。逆向第一步常做熵扫描:高熵 → 先脱壳再分析;低熵 → 可直接静态分析。
- **与字符串互证**:加壳程序往往同时表现为"明文字符串极少(Step 15)"+"熵很高(本步)"——两个独立信号互相印证,结论更可靠。这就是为什么专业工具(Detect It Easy、PEiD)会综合多个特征。
- **局限**:小段高熵(如嵌入的压缩资源、证书、随机种子)是正常的,不能仅凭一块高熵就断定加壳;要看**比例和连续性**。

## 8. 软件设计理念
**组合既有原语搭出新能力**。`entropy_blocks` 没有重写任何统计逻辑,而是把 Step 14 的 `chunks` 迭代和本步的 `shannon_entropy` **组合**起来:分块 → 各自算熵 → 收集。这是"小而纯的函数易于组合"的直接回报——`shannon_entropy` 是纯函数,所以能放心地在 `map` 里对每块调用,不担心副作用。设计 API 时优先做"小、纯、单一职责"的零件,复杂能力往往就是它们的组合。这也是整个模块 D 的缩影:hex_dump / extract_strings / entropy 各是一件独立瑞士军刀,可单用、可组合。

## 9. 小测验(自测)
1. 为什么测试熵值用 `(h - 8.0).abs() < 1e-9` 而不是 `h == 8.0`?
2. 全是同一个字节的数据,熵为什么是 0?256 种值均匀出现,熵为什么是 8?
3. 一个文件整体熵 7.9、且有大段连续高熵块,最可能说明什么?逆向时下一步该做什么?
4. 为什么用 `[usize; 256]` 数组统计字节频率,而不用 `HashMap<u8, usize>`?
5. 仅凭"文件里有一小块高熵数据"就断定它被加壳,合理吗?为什么?

## 10. 参考答案
1. 因为 `f64` 是二进制浮点,十进制小数和对数运算会有微小舍入误差,结果可能是 7.9999999999 而非精确的 8.0。用 `==` 比较几乎必然失败;改用"差的绝对值小于一个极小容差"来判断"足够接近"。**浮点永远不要用 `==`**。
2. 全同一字节:只有 1 种可能、概率 1,`-1·log2(1) = 0`,完全可预测 → 熵 0。256 种值均匀:每种概率 1/256,熵 = -256·(1/256)·log2(1/256) = log2(256) = 8 → 完全不可预测,达到 1 字节能承载的最大信息量。
3. 最可能是**加壳 / 加密 / 压缩**——大部分内容呈随机分布。逆向下一步应先**脱壳 / 解密**(动态运行让它自解压、再 dump 内存,或用对应脱壳工具),拿到原始低熵代码后再做静态分析,而不是直接反汇编那段高熵数据(那只是压缩 / 密文,反汇编没意义)。
4. 因为字节值域固定只有 256 种,定长数组用值当下标直接计数,**无需哈希、无堆分配**,更快更简单。`HashMap` 适合键空间大或未知的情况;这里键空间小且固定,数组是更优选择。
5. 不合理。小段高熵很常见且正常(内嵌的压缩资源、加密证书、随机数 / 密钥、图片等都是高熵)。判断加壳要看**高熵的比例和连续性**(大部分文件都高熵、大段连续),而非某一小块。单块高熵不足以下结论。
