# Step 14：hex dump(地址 + 十六进制 + ASCII 三栏)

## 0. 一句话目标
写一个 `hex_dump` 函数,把任意字节渲染成经典三栏视图:**地址 ｜ 16 个十六进制字节 ｜ 可见 ASCII**,不可打印字符用 `.` 代替。

## 1. 前置回顾
模块 A–C 我们把 Mach-O 结构解析得很透。但逆向时常常要"直接看原始字节长什么样"——这就是 hex dump,`xxd`/`hexdump -C`/各种十六进制编辑器的标配视图。它不依赖任何格式知识,对任意文件都能用,是模块 D(分析工具)的第一件瑞士军刀。

## 2. 先写测试(TDD·红)
```rust
#[test]
fn hex_dump_one_line() {
    let d = hex_dump(b"ABCD", 0);
    assert!(d.starts_with("00000000  41 42 43 44"));
    assert!(d.contains("|ABCD|"));
    assert_eq!(d.lines().count(), 1);
}
#[test]
fn hex_dump_non_printable_becomes_dot() {
    let d = hex_dump(&[0x00, 0x41, 0xff], 0);
    assert!(d.contains("|.A.|"));   // 0x00/0xff → '.';0x41 → 'A'
}
#[test]
fn hex_dump_multiple_lines_addresses() {
    let d = hex_dump(&vec![0u8; 20], 0x1000);  // 20 字节 → 2 行
    let lines: Vec<&str> = d.lines().collect();
    assert!(lines[0].starts_with("00001000"));
    assert!(lines[1].starts_with("00001010"));  // 第二行地址 +16
}
```

## 3. 实现到通过(TDD·绿)
```rust
use std::fmt::Write as _;   // 为了能对 String 用 write!/writeln!

pub fn hex_dump(bytes: &[u8], base: u64) -> String {
    let mut out = String::new();
    for (i, chunk) in bytes.chunks(16).enumerate() {   // 每 16 字节一组
        let addr = base + (i * 16) as u64;
        let mut hex = String::new();
        for (j, b) in chunk.iter().enumerate() {
            let _ = write!(hex, "{b:02x} ");
            if j == 7 { hex.push(' '); }               // 第 8 字节后多一个空格,视觉分组
        }
        let ascii: String = chunk.iter()
            .map(|&b| if b.is_ascii_graphic() || b == b' ' { b as char } else { '.' })
            .collect();
        let _ = writeln!(out, "{addr:08x}  {hex:<49}|{ascii}|");  // 十六进制列定宽 49 对齐
    }
    out
}
```
逐点讲:
- **`bytes.chunks(16)`**:把切片切成"每 16 个一组"的迭代器——hex dump 每行 16 字节的来源。最后一组可能不足 16 个,`chunks` 会原样给出短的一组(所以末行能正确处理零头)。
- **`.enumerate()`**:给每组配一个序号 `i`,用来算这一行的起始地址 `base + i*16`。
- **`write!(hex, "{b:02x} ")`**:往 `hex` 这个 `String` 里追加格式化文本。`{b:02x}` = 两位十六进制。要对 `String` 用 `write!`,需在作用域引入 `std::fmt::Write` trait(顶部那行 `use`)。`let _ =` 是因为 `write!` 返回 `Result`(写 `String` 不会失败),我们显式忽略它。
- **`is_ascii_graphic() || b == b' '`**:判断字节是否"可见"(可打印图形字符或空格);否则用 `.`。
- **`{hex:<49}`**:左对齐、最小宽度 49。16 字节 × "xx "(3 字符)= 48,加第 8 字节后的额外空格 = 49,把短行也补齐到等宽,ASCII 列才能对齐成一列。

## 5. 学到的语法 / 技巧
- **`.chunks(n)`**:把切片按每 n 个分组迭代,末组可短。
- **`.enumerate()`**:迭代时附带序号。
- **`write!` / `writeln!` 到 `String`**:需 `use std::fmt::Write`;像 `println!` 一样格式化,但写进字符串而非标准输出。
- **格式说明符**:`{:02x}`(两位十六进制)、`{:08x}`(八位十六进制地址)、`{:<49}`(左对齐定宽)。
- **`b.is_ascii_graphic()`**:字节是否为可见 ASCII 图形字符。
- **`.map(...).collect::<String>()`**:把字节序列转换并收集成字符串。

## 6. 语言设计巧思
**迭代器适配器:声明"要什么",而非手写"怎么循环"**。`bytes.chunks(16).enumerate()` 用两个**迭代器适配器**就表达了"每 16 个一组、带上序号"——没有手算下标、没有边界判断,末组不足 16 也自动处理对。相比 C 里手写 `for (i=0; i<len; i+=16)` 再小心处理末尾零头(差一错误的高发区),迭代器把意图直接表达出来,既不易错又可读。`.map(...).collect()` 同理:声明"每个字节怎么变、收集成什么",而不是手动 push。这种"组合小适配器搭出数据流水线"的风格,是 Rust(及现代语言)处理序列的主流范式。

**为什么用 `write!` 拼字符串而非 `+` 连接**:反复用 `+` 拼接字符串会产生大量临时分配;`write!` 直接往同一个 `String` 缓冲区追加,高效且清晰。`let _ =` 显式忽略其 `Result`,既消除"未使用结果"的警告(CI 的 `-D warnings`),也表明"我知道这里不会失败"。

## 7. 领域知识:hex dump 为什么是逆向标配
- **三栏对照**:左列地址(便于定位/交叉引用)、中列十六进制(看原始字节、字节序、对齐)、右列 ASCII(一眼认出字符串、路径、魔数文本)。三者并置,信息密度极高。
- **不依赖格式**:对任何文件都适用——加壳的、损坏的、私有格式的,先 hex dump 看看总没错。逆向遇到不认识的数据,第一反应往往就是"dump 出来肉眼扫一遍",找魔数、找可见字符串、找重复模式。
- **每行 16 字节、8 字节处分组**:是 `hexdump -C`/`xxd` 的事实标准,符合大多数人的视觉习惯(一行刚好一屏宽,16 是 2 的幂便于对齐)。
- 进阶工具会在此基础上加**彩色**(区分零字节/可打印/高位字节)、**ASCII/Unicode 智能识别**、**与反汇编联动**等,但内核就是这三栏。

## 8. 软件设计理念
**纯函数 + 返回字符串,而非直接打印**。`hex_dump` 不调用 `println!`,而是**返回一个 `String`**。好处:① **可测试**——测试直接断言返回值,不必捕获标准输出;② **可复用**——调用方爱打印就打印、爱写文件就写文件、爱嵌进别的输出就嵌;③ **无副作用**——同样输入永远同样输出,易推理。把"计算内容"和"决定怎么输出"分开(本函数只管前者),是让逻辑可测、可组合的关键设计习惯,和我们一贯的"库提供纯逻辑、main 负责 IO"一脉相承。

## 9. 小测验(自测)
1. `bytes.chunks(16)` 在字节数不是 16 倍数时,最后一组会怎样?为什么这对 hex dump 很方便?
2. 为什么 `hex_dump` 返回 `String` 而不是直接 `println!` 打印?列出至少两个好处。
3. `{hex:<49}` 里的 `<49` 是什么意思?去掉它,输出会出什么问题?
4. 要对一个 `String` 使用 `write!` 宏,为什么必须 `use std::fmt::Write`?
5. ASCII 列为什么把不可打印字节显示成 `.` 而不是原样输出?

## 10. 参考答案
1. 最后一组会是一个**长度不足 16 的短切片**(有几个给几个),`chunks` 不会补齐也不会丢弃。这对 hex dump 很方便:末行零头自动正确处理,我们只需在格式化时用定宽补齐对齐即可,无需手动判断"还剩几个字节"。
2. 好处:① **可测试**:测试直接断言返回的字符串,无需捕获 stdout;② **可复用**:调用方可自由选择打印 / 写文件 / 拼进别的输出;③ **无副作用 / 易推理**:纯函数,同输入同输出。(满足两个即可。)
3. `<49` 表示"**左对齐、最小宽度 49**"。十六进制列每行内容长度因末行零头而不同,用 `<49` 补足到等宽,ASCII 列才能整齐地对齐成一列。去掉它,末行(字节少)的十六进制列会变短,导致 `|ASCII|` 列错位、不对齐。
4. 因为 `write!`/`writeln!` 宏依赖目标类型实现了 `std::fmt::Write` trait 的方法(`write_str` 等)。`String` 确实实现了它,但**trait 的方法只有在该 trait 在作用域内时才能调用**,所以要 `use std::fmt::Write` 把它引入。
5. 因为原样输出控制字符(如 `\0`、`\n`、终端转义序列 `\x1b`)会**搞乱终端显示**甚至执行转义,且无可读意义。统一用 `.` 占位,既保持每个字节一列对齐,又让真正可读的字符突出出来,便于肉眼扫描字符串。
