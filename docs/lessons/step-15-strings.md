## 0. 一句话目标
扫描字节,把所有"长度 ≥ 阈值的连续可打印字符"片段抽出来(连同它们的偏移),复刻经典 `strings` 命令。

## 1. 前置回顾
Step 14 的 hex dump 让我们肉眼看字节。但人工翻字符串太慢——本步自动化它:程序里的路径、URL、错误提示、格式串、库名往往**直接暴露意图**,是逆向找线索的头号手法。我们扫一遍字节,把可读片段提取出来。

## 3. 实现到通过(TDD·绿)
```rust
pub fn extract_strings(bytes: &[u8], min_len: usize) -> Vec<(usize, String)> {
    let mut out = Vec::new();
    let mut start = 0;
    let mut cur = String::new();
    for (i, &b) in bytes.iter().enumerate() {
        if b.is_ascii_graphic() || b == b' ' {
            if cur.is_empty() { start = i; }      // 记下这段的起点
            cur.push(b as char);                  // 累积可打印字符
        } else if cur.len() >= min_len {
            out.push((start, std::mem::take(&mut cur)));  // 够长 → 收下并清空
        } else {
            cur.clear();                          // 太短 → 丢弃
        }
    }
    if cur.len() >= min_len { out.push((start, cur)); }   // 收尾:结尾那段
    out
}
```
这是一个**状态机式的扫描**:
- 维护"当前正在累积的片段 `cur`"和它的起点 `start`。
- 遇可打印字符:若 `cur` 为空就记起点,然后把字符追加进 `cur`。
- 遇不可打印字符(分隔):若 `cur` 够长就收进结果,否则丢弃,然后重新开始。
- **`std::mem::take(&mut cur)`**:把 `cur` 的内容**取走**(返回给我们),同时把 `cur` 原地重置为空 `String`。比"克隆一份再清空"高效——所有权直接转移,无拷贝。
- 循环结束后别忘了**收尾**:文件结尾可能还攒着一段没被分隔符触发。

## 5. 学到的语法 / 技巧
- **状态机扫描**:用循环 + 累积变量识别"连续满足条件的片段"。
- **`std::mem::take(&mut x)`**:取走 `x` 的值并把它替换为默认值(`String` 的默认是空串),零拷贝转移所有权。
- **`Vec<(usize, String)>`**:元素是元组 `(偏移, 字符串)`,一种轻量的"无名结构"。
- **`b as char`**:把一个 ASCII 字节转成 `char`(仅对 ASCII 安全,我们已用 `is_ascii_graphic` 保证)。
- **`for (i, &b) in bytes.iter().enumerate()`**:同时拿到下标 `i` 和字节值 `b`(`&b` 模式把引用解构成值)。

## 6. 语言设计巧思
**`std::mem::take` 与"移动语义"的妙用**。我们要"把 `cur` 的内容收进结果、同时让 `cur` 变空继续用"。天真写法是 `out.push((start, cur.clone())); cur.clear();`——多一次堆分配的克隆。`std::mem::take(&mut cur)` 利用 Rust 的**移动语义**:把 `cur` 里那块堆缓冲**整体搬走**塞进结果,并给 `cur` 装一个新的空 `String`(空串不分配堆)。零拷贝、且借用检查器满意(我们只是替换了 `cur` 的值,没有留下悬空引用)。这种"取走并留下默认值"的模式在 Rust 里极常见,是高效操控可变状态的标准招式。

**`Result`/`Option`/所有权之外,这里展示了 Rust 处理可变状态的另一面**:有时命令式的"循环 + 可变累积器"就是最清晰的表达(不必强行写成纯函数式链)。Rust 不排斥可变,只是要求可变是**受控、显式**的(`let mut`)。

## 7. 领域知识:strings 在逆向里的地位
- **头号侦察手段**:拿到陌生二进制,`strings` 几乎总是第一批命令之一。函数名(若没 strip)、文件路径、URL、IP、注册表键、SQL 语句、错误消息、版本号、加密常量名……往往直接出现在字符串里,瞬间暴露程序在干什么。
- **阈值的权衡**:`min_len` 太小(如 1–2)会混入大量噪声(随机字节里偶然连成的"字符串");太大会漏掉短而关键的串(如 "sh"、"/bin")。经典 `strings` 默认 4,我们 demo 用 6 以减少噪声。这是个**信噪比**的取舍。
- **局限**:只能找"明文"字符串。加壳 / 加密 / 混淆的程序,关键字符串常被加密,运行时才解密——这时 `strings` 看到的是乱码或没有,反而是"字符串异常少 / 全是乱码"本身成了"可能加壳"的线索(引出下一步:熵值分析)。
- **宽字符**:本实现只认单字节 ASCII;真实工具还会扫 UTF-16(Windows 程序大量用),那是 `\x00` 间隔的字符——可作为后续增强。

## 8. 软件设计理念
**把"策略"参数化:`min_len` 作为参数而非写死**。提取多长才算"字符串"是会变的策略(不同场景信噪比要求不同),我们把它做成参数 `min_len`,让同一份逻辑适配各种需求,而不是写死成 4 或 6。这呼应 Step 03 把"字节序"参数化的同一思想:**识别出会变的决策点,抽成参数,保持核心逻辑通用**。同时本函数仍是**纯函数**(输入字节+阈值 → 输出列表,无副作用),延续了"逻辑可测、IO 留给 main"的分层。

## 9. 小测验(自测)
1. `std::mem::take(&mut cur)` 相比 `cur.clone()` + `cur.clear()` 好在哪?
2. 为什么循环结束后还要单独写一句"收尾"处理 `cur`?不写会漏掉什么?
3. `min_len` 设得太小或太大各有什么问题?这是个什么权衡?
4. 一个程序如果 `strings` 几乎找不到有意义的明文字符串、或大片乱码,可能说明什么?
5. 本实现为什么对 Windows 程序里常见的 UTF-16 字符串可能"看不全"?

## 10. 参考答案
1. `clone()` 会**额外分配一块堆内存并逐字节拷贝**当前字符串;`std::mem::take` 利用移动语义,把 `cur` 已有的堆缓冲**整体搬走**塞进结果,并给 `cur` 换上一个不分配堆的空串。零拷贝、更高效,且让借用检查器满意。
2. 因为收集是"遇到不可打印字符才触发"的。如果一段可打印字符**一直延伸到文件末尾**、后面没有分隔符,循环内就永远不会触发收集。收尾那句专门把这最后攒着的一段(若够长)补收进来,否则会漏掉结尾的字符串。
3. 太小:大量随机字节偶然连成的短"字符串"混入,噪声多、难看;太大:漏掉短而关键的串(如 `/bin`、`sh`)。这是**信噪比**的权衡——要在"少漏"和"少噪声"之间取平衡。
4. 可能说明程序被**加壳 / 加密 / 混淆**了:关键字符串被加密存储、运行时才解密,所以静态扫描只看到乱码或极少明文。"明文字符串反常地少 / 多为乱码"本身就是"疑似加壳"的信号——正好引出下一步的熵值分析。
5. 因为 UTF-16 字符串里每个 ASCII 字符后跟一个 `\x00`(如 `h\0e\0l\0l\0o\0`)。本实现遇到 `\0`(不可打印)就中断累积,于是每个字母都被当成长度 1 的片段而被过滤掉,完整的宽字符串看不全。要支持需额外扫描 UTF-16 模式。
