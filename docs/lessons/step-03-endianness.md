# Step 03：读多字节整数,直面"字节序"

> 模块：A 基础 ｜ 对应提交：`<待回填>` ｜ 测试：✅ 通过 ｜ 上一步：[Step 02](step-02-byte-reader.md)

## 0. 一句话目标
给游标加上 `read_u16` / `read_u32` / `read_u64`:一次读多个字节、拼成一个更大的整数,并能按**大端 / 小端**两种字节序正确解读。最终把 Step 01 看到的 `cf fa ed fe` 还原成真实数值 `0xFEEDFACF`。

## 1. 前置回顾
Step 02 我们做了游标 `ByteReader`,它能安全地一次读**一个**字节(`read_u8`,越界返回 `None`)。但文件头里的字段大多是 2、4、8 个字节的整数(magic 魔数、入口地址、节区大小……)。本步在 `read_u8` 这块积木之上,拼出读多字节整数的能力。而一旦"多字节",就必须回答一个绕不开的问题:这几个字节,**谁在前、谁在后**?这就是"字节序"。

## 2. 先写测试(TDD·红)
最有说服力的测试,就是把 Step 01 的悬念解开:
```rust
let data = [0xcf, 0xfa, 0xed, 0xfe];   // 文件里看到的顺序
let mut r = ByteReader::new(&data);
assert_eq!(r.read_u32(Endian::Little), Some(0xFEED_FACF)); // 小端 → 真实魔数
```
再加一个对照,证明"同样的字节、不同字节序、不同结果":
```rust
assert_eq!(r.read_u32(Endian::Big), Some(0xCFFA_EDFE));    // 大端 → 完全不同
```
以及"字节不够要安全失败":
```rust
let data = [0x01, 0x02];               // 只有 2 字节
assert_eq!(r.read_u32(Endian::Little), None); // 凑不齐 4 字节 → None
```
此时 `read_u32` / `Endian` 还不存在,`cargo test` → **红**:

## 3. 实现到通过(TDD·绿)
### 3.1 先定义"字节序"这个概念 —— 一个 `enum`
```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Endian {
    Little, // 低位字节在前(x86 / ARM)
    Big,    // 高位字节在前(网络序 / 部分架构)
}
```
又是 Step 01 学过的 `enum`(还记得吗?用类型表达"只能是这几种之一")。这次多 derive 了 `Clone, Copy`——见 §6 解释为什么。

### 3.2 读 4 字节拼成 u32
```rust
pub fn read_u32(&mut self, endian: Endian) -> Option<u32> {
    let bytes = [
        self.read_u8()?,
        self.read_u8()?,
        self.read_u8()?,
        self.read_u8()?,
    ];
    Some(match endian {
        Endian::Little => u32::from_le_bytes(bytes),
        Endian::Big    => u32::from_be_bytes(bytes),
    })
}
```
逐块讲:
- **`endian: Endian`**:方法多收一个参数,告诉它"按哪种字节序拼"。
- **`[self.read_u8()?, ...]`**:连续调用 4 次上一步的 `read_u8`,把结果装进一个长度为 4 的数组 `[u8; 4]`。每个 `?` 都是一道保险:任何一次越界(`None`),整个 `read_u32` 立刻返回 `None`——这就是 §2 第三个测试"字节不够 → None"能通过的原因。**注意我们复用了 Step 02 的 `read_u8`,没有重写边界检查**,这正是封装的回报。
- **`match endian { ... }`**:`match` 是 Rust 的"超级 switch"。按 `endian` 的值分两路。`match` 也是表达式,它求值出来的整数就是 `Some(...)` 里的内容。
- **`u32::from_le_bytes(bytes)` / `from_be_bytes(bytes)`**:标准库自带的转换——把一个 `[u8; 4]` 按小端 / 大端拼成 `u32`。`le` = little-endian,`be` = big-endian。我们不用自己写位移和按位或,标准库给好了。

`read_u16` / `read_u64` 同理(分别读 2 / 8 字节)。`read_u64` 里用了个小技巧:
```rust
let mut bytes = [0u8; 8];
for slot in bytes.iter_mut() {
    *slot = self.read_u8()?;
}
```
`[0u8; 8]` 先建一个 8 个 0 的数组;`iter_mut()` 拿到每个槽位的可变引用,逐个填进读到的字节。比手写 8 行 `read_u8()?` 干净。

`cargo test` → **✅ 绿**:
```
test result: ok. 9 passed; 0 failed
```

## 5. 学到的语法 / 技巧
- **`enum Endian`**:再次用枚举表达封闭集合(只有大端 / 小端两种)。
- **方法带参数**:`read_u32(&mut self, endian: Endian)`——`&mut self` 之后可以像普通函数一样收更多参数。
- **数组字面量 `[a, b, c, d]` 与 `[0u8; 8]`**:前者直接列出元素;后者是"8 个 0"的简写。数组类型写作 `[u8; 4]`(元素类型 + 长度)。
- **`match` 表达式**:按一个值的不同情况分支,且能"求值"出结果。
- **`u32::from_le_bytes` / `from_be_bytes`**:标准库把字节数组按字节序拼成整数。
- **`.iter_mut()` + `*slot = ...`**:遍历并**修改**数组每个元素;`*` 解引用后赋值。
- **`0xFEED_FACF` 里的下划线**:数字分隔符,纯粹为了好读,等于 `0xFEEDFACF`。

## 6. 语言设计巧思
**`Copy` 语义与"移动 vs 复制"**。我们给 `Endian` derive 了 `Clone, Copy`。这牵涉 Rust 又一核心规则:默认情况下,把一个值赋给别人或传进函数,会发生**移动(move)**——原来的变量就**不能再用**了(所有权转移走了)。这对大对象是好事(避免偷偷的深拷贝),但像 `Endian` 这种只有"两选一"、小到不能再小的值,移动反而别扭:我们在 `read_u16`、`read_u32` 里都想用同一个 `endian`,要是一传就"失效"就麻烦了。

`#[derive(Copy)]` 告诉编译器:"这个类型小且简单,传递时**直接按位复制一份**,别走移动。"于是 `endian` 传进 `match` 后,原值依然可用。**经验法则**:像数字、`bool`、小枚举这种"轻量、无需清理"的类型,给它们 `Copy`;像 `String`、`Vec` 这种"持有堆内存、需要清理"的类型,**不能** `Copy`(否则就成了昂贵的隐式深拷贝),只能 `Clone`(显式调用 `.clone()`)。这套"移动默认、复制可选"的设计,是 Rust 既高效又安全的关键——你几乎不会有"无意间的昂贵拷贝"。

**为什么不自己写位运算?** 拼字节其实是 `(b0 << 24) | (b1 << 16) | ...` 这类位移或运算,极易写错方向。标准库的 `from_le_bytes` / `from_be_bytes` 把"正确性"封进了名字里——你只需选对字节序,剩下的交给久经考验的标准库。这体现了"优先用标准库经过验证的原语,而不是重造易错的轮子"。

## 7. 领域知识:字节序(endianness)
这是逆向工程**天天**要面对的概念,务必建立直觉。

一个 4 字节整数 `0xFEEDFACF`,它的四个字节从高位到低位是:`FE`(最高)、`ED`、`FA`、`CF`(最低)。把它写进文件 / 内存时,有两种排法:

| 字节序 | 文件里的字节顺序 | 助记 |
|---|---|---|
| **小端 Little-endian** | `CF FA ED FE`(**低**位字节在**前**) | "低位在前",x86 / ARM / 大多数 PC |
| **大端 Big-endian** | `FE ED FA CF`(**高**位字节在**前**) | "高位在前",网络协议 / 部分 RISC |

所以 Step 01 我们在 macOS 二进制开头看到 `cf fa ed fe`,正是 `0xFEEDFACF` 的**小端**存法——这下完全对上了。

**为什么逆向必须搞清楚它**:同一段字节,字节序选错,所有解析出来的数值(地址、偏移、大小)全是错的,后续分析满盘皆输。每种文件格式 / 架构都有约定:Mach-O、PE 基本是小端;ELF 在文件头里**用一个字节字段声明自己是大端还是小端**,解析器要先读这个字段、再决定后面怎么读——这正是我们的 `read_u32(endian)` 把字节序做成"参数"的现实意义:同一个解析器,既能读小端文件,也能读大端文件。

## 8. 软件设计理念
**复用底层原语 + 把变化点参数化**。`read_u16/u32/u64` 全部架在 `read_u8` 之上,边界检查只在一处(`read_u8`)实现,上层自动继承安全性——这是 Step 02 "封装"埋下的复利。而"字节序"是会变的东西(不同格式不同),我们没把它写死,而是做成**参数** `endian: Endian`,让同一份代码适配两种情况。"识别出不变的核心逻辑、把变化的部分抽成参数",是写出可复用代码的基本功。

## 9. 小测验(自测)
1. 字节 `00 00 00 01` 按小端读成 u32 是多少?按大端呢?
2. `read_u32` 里四个 `read_u8()?` 的 `?` 起什么作用?如果文件只剩 3 个字节,`read_u32` 返回什么?
3. 为什么给 `Endian` 加 `#[derive(Copy)]`?如果不加,`read_u32` 里把 `endian` 用进 `match` 会发生什么?
4. ELF 文件如何告诉解析器自己是大端还是小端?这对"先读什么"有什么影响?
5. 为什么用标准库的 `from_le_bytes`,而不是自己写 `(b0<<24)|(b1<<16)|...`?

## 10. 参考答案
1. 小端"低位在前",所以 `00 00 00 01` 的最低字节是最后那个 `01`?——不,小端是**第一个字节为最低位**:`00`(最低)、`00`、`00`、`01`(最高)→ `0x01000000` = 16,777,216。大端"高位在前":第一个字节 `00` 为最高位 → `0x00000001` = 1。(这题专门让你体会:同样字节,字节序不同,数值天差地别。)
2. 每个 `?` 都是"越界即提前返回 `None`"的保险。文件只剩 3 字节时,第 4 个 `read_u8()?` 拿到 `None`,`read_u32` 立刻整体返回 `None`,不会读到不存在的字节。
3. 因为 `Endian` 很小很简单,`Copy` 让它传递时按位复制而非"移动失效",这样 `endian` 传进 `match` 后原值仍可用。不加 `Copy` 也能编过(`match` 只是读它),但一旦在多处使用就容易遇到"value moved"的报错;给小枚举加 `Copy` 是惯例,省心。
4. ELF 头里有一个字节(`EI_DATA`)声明字节序:`1` = 小端、`2` = 大端。解析器必须**先**读这个字段,才能决定后面所有多字节字段按大端还是小端读。这正是把字节序做成参数的价值。
5. 自己写位移极易搞错移位量和方向(尤其大小端切换时),且不同整数宽度要各写一遍。`from_le_bytes` / `from_be_bytes` 是标准库验证过的原语,名字即语义,选对字节序即可,杜绝了一类隐蔽 bug。
